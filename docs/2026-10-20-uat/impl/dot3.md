### Mục còn lại sau review lượt 2
- **P3** `apps/miniapp/src/pages/cart.tsx:477-478 (with apps/miniapp/src/utils/cart-rules.ts:8 and cart.tsx:119-121)`: The comment and the worker's decision say the Thành tiền line stays hidden while the change waits for the debounce and the PATCH. That only holds for the 380ms debounce. After that, onMutate applies recompute() optimistically, which sets line.quantity = qty and line.total = unitPrice * qty. That makes localQty === line.quantity, so the line shows again with the number the client multiplied itself while the PATCH is still in flight. Example: a flash line at 50.000đ goes from SL 2 to 3. After 380ms the line shows 'Thành tiền 150.000đ'. If the server repriced because the flash allocation ran out, the number only corrects when the response arrives. This briefly shows the same client figure as the old code, then corrects itself, and the subtotal is also optimistic, so it is not a P2. The new spec only covers the moment right after the click (the debounce window), not the PATCH window. — Sửa: Choose one: (a) correct the comment and the report to say it is hidden only during the debounce and the in-flight number is the client estimate, or (b) hide the line while update.isPending for that line (pass a pending flag into CartLineRow). Add a spec: advance fake timers past 380ms while the PATCH promise has not resolved, and assert there is no 150.000đ.
- **P3** `apps/miniapp/src/components/checkout/address-section.tsx:43`: The condition changed from the old !editing (an address object derived from the list) to editingId === null. If editingId points to an address that has dropped out of the list (deleted on another screen, then the ['addresses'] query refetches while the form is open), the form disappears because editing is null. editingId is still non-null, so the legacy-address warning for the selected card also stays hidden. The customer then has neither the form nor the button to fix the address. Very unlikely in practice. — Sửa: Use editing === null (the derived object, as in the original code) instead of editingId === null. The new spec 'đang mở form sửa thẻ 1...' still passes.

### Mục còn lại sau review lượt 2
- **P3** `apps/api/src/modules/cart/cart.service.ts:400`: addItems now upserts every accepted line in one interactive transaction, in the order the lines arrive. Two repurchases from the same user running at once on two different orders that share variations in the opposite order (A adds v1 then v2, B adds v2 then v1) each lock a row or unique-index entry the other needs next. Postgres detects the deadlock and aborts one transaction, so that request returns 500 and adds nothing. The old code ran one small transaction per line and could not deadlock this way. Likelihood is low: it needs the same user to double-tap repurchase on two orders. — Sửa: Sort `accepted` by variationId before the upsert loop so every transaction takes locks in the same order. Keep `outcomes` in the original order (it is already computed before the transaction).
- **P3** `apps/api/src/modules/orders/orders.service.ts:504`: inCart is incremented for a line before addItems confirms it. Example: an order has two lines for the same variation v1, and line 1 is rejected by addItems because stock changed between the read and the write. Line 2 was already clamped as if line 1's quantity were in the cart, so it may end up partial with a smaller quantity than was really available. The old code incremented inCart only after addItem succeeded. This is a rare edge case and no money is involved. — Sửa: Optional. Leave as is, or on a rejected line recompute the room for later lines of the same variation. A simpler variant: let addItems clamp the quantity itself using qtyInCart.
- **P3** `apps/api/src/modules/catalog/catalog.service.ts:345`: When the cache is full (500 keys) and the key being refreshed is the current product's own expired entry, the code still deletes the oldest key, which belongs to another product, before calling set on the existing key. A still-valid entry is evicted for no reason, and expired keys are only removed when the cache is full. No wrong data is returned; it only causes extra queries. — Sửa: Evict only when `!this.boughtTogetherCache.has(product.id)`. Optionally delete the entry first and set it again so the order is LRU-like.
